# 持续 AI 辅助开发流程

[开发入口](../START_HERE.md) · [AGENTS](../AGENTS.md) · [路线图](ROADMAP.md)

## 一次任务的最小上下文

读取路线中的一个任务、对应能力行、相关架构段、实际源码及受影响测试。先记录基线 HEAD 和工作树状态，再写一句验收目标。例如：“修复同一连接登录切换后继承旧观察窗口，原版连续操作不被阻断。”不要每次都把全部历史台账塞进上下文。

任务交接包含：任务编号、当前提交、已改模块、实际命令与结果、未解决问题、下一步。未完成内容留在同一个任务中，不再生成新的总计划。

## 分工与并行

解析/适配、纯规则、持久化、测试/文档可以按文件所有权并行；同一个大型入口或状态机由一个集成者修改。跨域接口先写清字段语义与信任来源，再让其他任务实现。每个分支都有可独立审查的差异。

允许在授权隔离环境准备状态、调用内部方法和读取原生字段。通用测试脚手架仍属于独立 Terraria MCP；本仓库只维护 AntiCheat 使用侧，不为每条规则重建客户端自动化平台。

## 新规则模板

在设计或 PR 描述中回答以下问题，不必为每个小修复再新建文件：

| 项目 | 必须说清的内容 |
| --- | --- |
| 输入 | 包号/原生事件、完整解析条件、客户端声明与服务端事实 |
| 主体 | 账号如何绑定；登录切换、重连、槽位复用怎么办 |
| 目标 | NPC/物品等目标是否有代际；自然变化是否会误增代际 |
| 合法例外 | 哪些正常机制会产生相同表象，如何排除或降级 |
| 状态 | 窗口、容量、过期、FIFO、线程和卸载清理 |
| 输出 | 观察、输入拒绝、资源限制、服务踢出或永久处罚，不能混称 |
| 验证 | 最小正例、关键反例、实际经过的解析/Hook/持久化边界 |

没有足够事实时实现有界观察也是合格交付，但功能表必须标成观察，不能标成防护完成。

## 重构顺序

先做机械目录迁移并保持测试，再抽取接口/状态，最后改行为。新代码使用领域名称；旧 `M*` 类名、规则 ID、配置键和反射入口分开评估，避免仅为美观破坏数据与调用兼容。针对本目标版本的数据兼容不等于恢复旧游戏版本兼容。

每次变更优先跑受影响测试，再跑公共集合。没有变化的原生运行资格不必每次重新做所有历史场景；影响上下文、接线、线程或运行锁时必须重验对应部分。

## 文档职责

README 是概览；STATUS 是能力边界；ROADMAP 是下一步；ARCHITECTURE 是代码地图；BUILDING/CONFIGURATION 是可操作说明；REVIEW 是发现及审查范围。不要在多个文件复制长篇任务清单。

功能表的唯一结构化来源是 `capabilities.json`，通过仓库检查脚本生成。该脚本验证展示一致与路径存在，**不会证明代码语义与人工填写的状态一致**，仍需代码审查。

## 已确定的设计约束

**DEC-001：观察与处罚分离。** 不确定性保留为不确定性；有界日志和资源拒绝不作为累积分定罪。

**DEC-002：源码公开不等于产物接纳。** 公共单测、原生运行验证、GUI 场景和正式发布分别记录，运行包变化不自动继承旧资格。

**DEC-003：保留分层，渐进模块化。** 不重写 Core/Rules/Persistence 基础，也不为旧阶段再建平行实现。退役内容先确认引用和许可证后移出活动产物。

**DEC-004：先闭合重点场景。** 允许有限损失后的完整证据与处置；完整伤害、全物品来源和通用回滚继续冻结。

重大改变这些决定时在本文件记录替代决定、理由、验证与迁移，不只修改提示词或 README 宣传文字。
