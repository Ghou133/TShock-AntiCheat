# 长期开发路线

[首页](../README.md) · [实际功能](STATUS.md) · [开发流程](DEVELOPMENT.md)

这份路线管理后续工作，不将历史阶段的“已完成”自动搬成当前成果。没有百分比目标，也不为了增加覆盖率恢复已退出或冻结的能力。

## 当前优先顺序

**R0 工程可检查 → R1 运行包可复现 → R2 结构可维护 → R3 重点行为可验证 → R4 可发布与长期回归。**

R1 与 R2 的非冲突任务可并行，R3 的纯规则测试和场景设计不必等待全部重构。每个任务只在满足自身依赖后进入；遇到外部运行包阻塞，继续做公共测试、文档和独立模块，不停止整个项目，也不虚报原生成功。

状态只用：待办、进行中、受阻、待验收、完成。完成须有源码提交及实际验证记录。当前工程整理有初始实现，不能据此宣布整个 R0 完成。

## R0 · 公开工程基线

| 编号 / 状态 | 工作 | 验收标准 |
| --- | --- | --- |
| R0-01 · 待验收 | README、入口、能力登记、路线、架构、配置与 AI 约定 | 新读者无需旧对话就能说明项目目标、运行限制和下一任务；生成表与数据一致 |
| R0-02 · 待验收 | 公共过滤器、SDK 选择、Windows/Linux CI、文档检查 | 干净 checkout 可运行五个公共测试项目；失败/平台跳过清晰列出，不使用 continue-on-error |
| R0-03 · 待办 | 修复隐式本机路径、缺失依赖提示及测试根目录定位 | SDK/依赖缺失时有明确诊断；不依赖废弃文档作项目根标记；打包数据路径与运行读取一致 |
| R0-04 · 待办 | 公共文件与许可清理 | 新文档无测试工具品牌/对标叙事；历史材料、夹具、生成数据逐项分类；保留必要许可与可再现输入 |

相关入口：`global.json`、`AntiCheat.Public.slnf`、`.github/workflows/public-ci.yml`、工程文件、`tools/repository-checks`。不要因为某个旧测试失败就把整个测试项目从公共过滤器移除。

## R1 · 运行包与生产登记可复现

| 编号 / 状态 | 工作 | 验收标准 |
| --- | --- | --- |
| R1-01 · 受阻 | 清点外部 TShock/TSAPI/OTAPI 补丁，提供可公开的锁文件和构建步骤 | 新环境从明确来源与补丁得到可验证运行包；列出仍不能公开的输入及替代获取方式，不上传受限程序集 |
| R1-02 · 受阻 | 重建每条生产登记的审计链 | 登记包含规则版本、运行指纹、源码范围、合法反例、原生/客户端验证引用；缺失证据的规则不能新增或继承资格 |
| R1-03 · 待办 | 宿主 CLR 与依赖维护策略 | 评估受支持补丁版本，在新运行包复验后更新锁；不让老 CLR 精确锁变成永久不升级的理由 |
| R1-04 · 待办 | 原生故障测试与依赖清单 | 已知可能崩溃进程的用例独立运行，缺失源码依赖单独报告；能运行 Adapter 的受影响子集而不依赖真实服 |

当前阻塞是仓库外的定制补丁、未公开审计资料及精确运行包复现，不是代码数量不足。`TargetRuntime` 与 `M2RuleRegistry` 的锁和资格变更必须独立审查。

## R3 · 有限高价值能力逐项闭环

所有任务共同要求：正常场景、违规正例、取消与身份切换、重连/代际、容量与过期反例。目标是可解释的观察或处置，不是所有任务都必须得到永封。

| 编号 / 状态 | 当前起点 | 下一步与完成条件 |
| --- | --- | --- |
| R3-01 · 待办 | NPC 跨目标序列仅观察；独立候选预算存在 | 分开验证极端阶段伤害与普通批量打击。为原版穿透、多目标、同 tick 批量输入、合法高伤和死亡结算建立反例；归因/非法性不足继续观察，不能仅凭死亡或 overkill 永封 |
| R3-02 · 待办 | 地面物品异常清除仅观察 | 闭合真实请求到原生删除、物品代际与账号身份；密集拾取、远程机制、取消返程、移动与堆叠变化不得借给异常链。先完成原生观察，再独立审查控制资格 |
| R3-03 · 待办 | 世界编辑与粒子有限预算 | 测试正常高速建造、小范围操作、爆炸/连锁与批量刷入的边界；分离单连接/全局成本。只宣称有界工作限制，不扩展为完整世界模拟或回滚 |
| R3-04 · 待办 | 有限生命同步候选，TestLab 可服务踢出 | 增加切屏/重连、治疗、SSC 初次同步、自然免伤和 Buff 例外；一点伤害服务违规以踢出验证，不升级永久封禁；通用锁血结论需额外事实 |
| R3-05 · 待办 | 有限召唤与哨兵类型 | 明确实体数与槽位成本，核对版本最大值和自然生成先于退休的瞬态；覆盖常见类型后再评估身份清晰的硬上限处罚，Buff 单独不定罪/免检 |
| R3-06 · 待办 | 物品结构、进度与有限奖励观察 | 做版本化物品 ID、maxStack 和简单上下文；不能用“9999”这个字面值统一定罪。验证容器、拾取、消耗与合法例外，不建设全来源账本 |

真实客户端验收允许先发生有限损失再完成证据和处罚，不要求为了“零损失”不断扩充模型。由测试脚手架准备合成状态；涉及原版客户端行为的结论再补对应 GUI 场景。

## 完成的定义

纯文档任务可由内容检查与审阅完成。纯规则修复由失败回归、修复后通过和合法反例完成。原生接线与处罚任务还需匹配运行包、当前构建和实际边界证据。发布任务另需维护者批准；不把这些不同任务都卡在同一场 GUI 测试上。

新的长期目标优先加入既有任务或在此建立稳定编号。不要再创建与本表竞争的主路线、72 项覆盖率或按运行轮次扩张的总报告。
